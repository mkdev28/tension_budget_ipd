def create_schema_sqlite(db_connection: sqlite3.Connection):

    """

    Initializes the TensionBudget relational database tables and views on a SQLite connection.

    Also executes non-breaking schema migrations for existing database files.

    """

    cursor = db_connection.cursor()

    for ddl_stmt in SQLITE_DDL:

        cursor.execute(ddl_stmt)

    # Ensure existing SQLite tables receive the password-gating integrity columns

    try:

        cursor.execute("ALTER TABLE user_profiles ADD COLUMN password_hash TEXT;")

    except sqlite3.OperationalError:

        pass

    try:

        cursor.execute("ALTER TABLE user_profiles ADD COLUMN created_via TEXT DEFAULT 'desktop_registration';")

    except sqlite3.OperationalError:

        pass

    db_connection.commit()

 

 

def get_postgres_ddl() -> List[str]:

    """

    Returns equivalent PostgreSQL DDL statements for cloud database setup.

    """

    pg_ddl = []

    for stmt in SQLITE_DDL:

        s = stmt.replace("INTEGER PRIMARY KEY AUTOINCREMENT", "SERIAL PRIMARY KEY")

        s = s.replace("CREATE VIEW IF NOT EXISTS", "CREATE OR REPLACE VIEW")

        pg_ddl.append(s.strip() + "\n")

    return pg_ddl

A wearable bilateral EMG system that forecasts a user's subjective strain/discomfort **before it occurs**, giving enough lead time to rest or adjust — rather than only detecting strain after the fact.

## 5. ML pipeline — full step-by-step

### Phase 0 — Data preparation before the model

0.1 Data pulled from `v_ml_training_pairs` (pre-joined).

0.2 Filter: only rows where the **target** epoch has `strain_reported = 1`.

0.3 **Lagged pair construction** — self-join `epoch_features` on `session_id`, offsetting `epoch_index` by lead time `h`: predictors at time *t*, label at time *t+h*.

0.4 **Trend feature construction** — trailing-window slopes (e.g. over epochs t-2, t-1, t) appended as extra predictors, since forecasting needs trajectory, not just current state.

0.5 **Feature selection** (not "demographic join" — already handled by the view) — decide which pre-joined demographic columns to retain as covariates.

### Phase 1 — Pre-training prep

1.1 **Grouped split** — train/val/test split at the **session or user level** (never row-level, to avoid leakage from within-session autocorrelation). Primarily relevant to the Macro path.

1.2 **Standardization** — features scaled to zero mean/unit variance.

1.3 **Missing value handling** — incomplete DSP rows dropped/flagged.

1.4 **Hierarchical indexing** — each row tagged with integer user index `u`.

### Phase 2 — Model definition

```

strain[u, t+h] ~ Normal(μ, σ)

μ = α[u] + Σ_k β[u,k] × feature_k[t] + β_trend[u] × trend(feature[t-2:t])

α[u]      ~ Normal(α_pop, τ_α)          # per-user baseline (random intercept)

β[u,k]    ~ Normal(β_pop[k], τ_β[k])    # per-user sensitivity (random slope)

β_pop[k]  ~ Normal(0, λ_k² × τ²)        # population weight (Horseshoe-shaped)

λ_k       ~ HalfCauchy(0, 1)            # local shrinkage, per feature

τ         ~ HalfCauchy(0, τ_0)          # global shrinkage strength

τ_α, τ_β[k] ~ HalfNormal(...)

σ         ~ HalfNormal(...)

```

### Phase 3 — Hyperparameters (chosen/tuned, not learned)

| Hyperparameter | How tuned |

|---|---|

| Lead time `h` | Test candidate values (5/10/15 min) against forecast usefulness |

| Trailing window size | Test 2–4 epochs |

| Horseshoe `τ_0` | Set from expected number of "real" predictive features |

| `STRAIN_THRESHOLD`, `CONFIDENCE_REQUIRED`, `HARD_SAFETY_CEILING` | Tuned against labeled outcomes — a policy layer, separate from model fitting |

| NUTS: chains, draws, tuning steps, target acceptance | PyMC defaults; adjusted only if diagnostics (below) fail |

### Phase 4 — NUTS sampling (Macro path only)

4.1 Initialize multiple chains (e.g. 4).

4.2 Warm-up — adaptively tunes step size and mass matrix.

4.3 Sampling — Hamiltonian trajectory expansion; stops itself at a "U-turn" or divergence (no manual tuning of step count needed) — this is what "No-U-Turn" means.

4.4 Output: thousands of samples per parameter — this collection **is** the posterior.

4.5 Diagnostics — R-hat ≈ 1.0, effective sample size, divergence count. If diagnostics fail → adjust hyperparameters/priors → resample (loop back to Phase 3/4).

### Phase 5 — Validation (Macro path only)

5.1 Posterior predictive check on held-out sessions/users.

5.2 Metrics: point accuracy (e.g. MAE), **calibration check** (does the 90% credible interval actually contain the true value ~90% of the time?), comparison against the `composite_score` heuristic baseline.

### Phase 6 — Storage

Posterior summaries (mean, SD, credible intervals) written to a cloud `model_weights` table — per-user records + one shared population record.

### Phase 7 — Inference (no NUTS, reads stored weights only)

New epoch → lookup stored posterior for that user → compute posterior predictive distribution for `t+h` → pass to the alert policy layer.

### Phase 8 — Retraining triggers (branch **before** any sampling, not after validation)

```

Indexing > Macro Trigger: [24–72h OR 500+ new labels]

Indexing > Micro Update:  [per new user label]

// Macro path — full pipeline

Macro Trigger > Model Graph > Hyperparameters > NUTS Sampler > Diagnostics

Diagnostics > Validation: [YES]

Diagnostics > Hyperparameters: [NO] Adjust settings, resample

Validation > Model Weights: Overwrites ALL parameters

// Micro path — lightweight, bypasses NUTS entirely

Model Weights > Micro Update: Reads fixed β_pop[k], τ_β[k] (anchor)

Micro Update > Model Weights: Writes updated α[u], β[u,k] ONLY

```

### The data flywheel (closes the loop)

```

Alert Policy > User Label: system alerts user

User Label > Raw Storage: [strain_reported = 1] feeds back to cloud

```

A forecast triggers an alert → user responds with a real label → becomes tomorrow's training data.

## 6. Macro vs. Micro — full comparison

| | Macro (full retrain) | Micro (lightweight update) |

|---|---|---|

| Scope | Every user + population, jointly | One user only |

| What's held fixed | Nothing — fully resampled | `β_pop[k]`, `τ_β[k]` frozen at last Macro's values |

| What's updated | `α[u]`, `β[u,k]` for all users + `α_pop`, `β_pop[k]`, `τ_α`, `τ_β[k]`, `λ_k`, `τ` | Just that one user's `α[u]`, `β[u,k]` |

| Method | Full NUTS, thousands of draws, multiple chains, diagnostics, validation | Small, fast single-user Bayesian update — no NUTS, no diagnostics |

| Trigger | Every 24–72h, or once ≥500 new labeled epochs accumulate | Per new labeled epoch (runs immediately) |

| Why this cadence | Expensive — must be batched; freshness vs. cloud-compute-cost trade-off | Cheap — no cost reason to delay; personalization should feel responsive, not lag days behind |

| Runs where | Cloud compute instance (e.g. AWS EC2), spun up for the job, torn down after | Cloud (always) — needs shared `model_weights` read/write access; not run on-device |

**Personalization never fully replaces the population anchor.** As a user logs more data, `β[u,k]` is pulled increasingly toward their own evidence and increasingly less toward `β_pop[k]` — but the anchor is never removed from the model definition, even for long-time users. This is intentional: it protects against a handful of noisy/unusual personal data points swinging predictions wildly. This is the core benefit of **partial pooling** (vs. "no pooling," i.e. a fully separate model per user, which was explicitly rejected).

**Network effect:** later users benefit from a more-refined population baseline built from everyone who came before them and had enough Macro-retrain-cycle data — but this only holds if periodic retraining actually happens, and only helps proportionally to how similar a new user is to the existing population.

## 7. Alert decision logic (policy layer, not learned by the model)

```

Every epoch:

  posterior = predictive_posterior(model, user=u, features_now, lead=h)

  P_over = fraction(posterior > STRAIN_THRESHOLD)

  if P_over >= CONFIDENCE_REQUIRED:

      fire_alert()

  if percentile(posterior, 95) >= HARD_SAFETY_CEILING:

      fire_conservative_alert()   # catches high-uncertainty, high-danger cases

```

- `STRAIN_THRESHOLD` (e.g. 7.0) — justified by the app's own CR-10 scale labeling 7 as "Very strong (Severe strain)," not an arbitrary or borrowed number.

- `CONFIDENCE_REQUIRED` (e.g. 0.85) — the dial controlling false-alarm vs. missed-danger trade-off; only possible because the model outputs a range, not a point estimate.

- The model predicts the distribution; the threshold and confidence level are **policy decisions**, not learned parameters.

## 8. Composite score (parallel, non-ML heuristic)

- Hand-built formula (Koch equations + asymmetry + SUMA penalty), fixed weights, no real strain data behind it originally.

- Computed on-device (phone) in real time, alongside the DSP features — not dependent on the ML pipeline to produce a number.

- Can be **recalibrated periodically** using the ML model's learned weights (`β_pop`, or per-user `β[u,k]`) — replacing guessed coefficients with data-derived ones. This is effectively distilling the expensive Bayesian model into a cheap, fast formula usable between retrains.

## 9. Why Bayesian hierarchical + Horseshoe + NUTS (and not alternatives)

| Choice | Why | Beats |

|---|---|---|

| Bayesian (posterior, not point estimate) | Honest uncertainty, essential with sparse/opt-in labels; enables the confidence-threshold alert rule | Point-estimate models (regression, Random Forest, plain NN) are confidently wrong when data is thin |

| Hierarchical (per-user + population) | Partial pooling — personalizes while borrowing strength from the group | Complete pooling (ignores individual differences) and no pooling (unstable with little per-user data) |

| Horseshoe prior | Automatic, interpretable feature selection across ~35 correlated features | PCA (destroys interpretability), Lasso/Ridge (fixed, non-adaptive shrinkage) |

| NUTS | Efficiently samples the full posterior via Hamiltonian dynamics; self-tuning (no manual step-count tuning) | Gradient descent (one point, no uncertainty), Metropolis-Hastings (too slow in high dimensions) |

### Why not a neural network (explicit trade-off, not just "NNs are heavy")

- NNs give point predictions natively; calibrated uncertainty requires extra machinery (Bayesian NNs, MC Dropout, deep ensembles) that's harder to implement and often poorly calibrated regardless.

- NNs are data-hungry; personalizing per user (embeddings or per-user layers) needs far more labeled data per person than this project's sparse, opt-in labeling realistically provides.

- NNs are a black box — explaining *why* a prediction was made requires bolting on separate tools (SHAP/LIME) after the fact, vs. a hierarchical model's weights being directly readable.

- With a small, sparse dataset, NNs are prone to overfitting/memorizing noise; the Horseshoe prior's regularization is explicitly designed to handle exactly this data regime.

- **Honest caveat:** this calculus could shift with much more data — NN flexibility becomes more attractive as data volume grows. The choice is scoped to the current data regime and requirement (calibrated uncertainty + per-user personalization on sparse data), not a blanket claim that NNs are inferior in general.

## 1. How much data do you need before training?

There's no single magic number, but there is real methodological literature on minimum sample sizes for hierarchical/multilevel models, and it applies directly to your architecture.

The most commonly cited threshold in the multilevel modeling literature: the probability that a model will not converge can be quite high when the number of groups is low (fewer than 30-50) and the number of cases per group is small (5-20). More specifically, most simple models with 50 or more groups and approximately 5-10 cases per group will not have convergence problems, while with fewer than 5 cases per group and fewer than 50 groups, standard errors for fixed effects will be too small, inflating false-positive risk, and random effect estimates become unreliable.

**How this maps to your project:**

- "Groups" = your users. "Cases per group" = labeled epochs per user.

- The frequentist thresholds above (50 groups, 5–10 cases each) are a *conservative reference point*, not a hard requirement for you — because Bayesian estimation is explicitly noted in this literature as a way to make small-cluster situations more tractable than classical (maximum-likelihood) approaches, since priors regularize estimates that classical methods can't stabilize with few groups.

- **Realistic honest minimum for your class project:** aim for **at least 8–10 users**, each with **at least 8–10 labeled epochs**, before you run a full model and call the results meaningful. Below that, you can still technically run NUTS and get a posterior — but the posteriors will be very wide, group-level variance (`τ_α`, `τ_β[k]`) will be poorly estimated, and you should present results as "preliminary, demonstrating the pipeline works" rather than "our model accurately predicts strain."

- If you have fewer than ~5 users, don't try to demonstrate the *hierarchical/personalization* benefit yet — demonstrate the *pipeline mechanics* (data flows in, NUTS converges, posterior comes out, alert logic works on it) using a simpler pooled or single-user model, and be upfront that hierarchical personalization needs more subjects to actually show its value.

**What to check before training, not guess:** how many users you have, and for each, how many epochs have `strain_reported = 1`. If some users have 1–2 labels, keep them in the dataset (partial pooling handles this gracefully) but don't expect their personal `β[u,k]` to mean much yet.

## 2. How you should actually proceed — a professional Bayesian workflow, not ad hoc

This is a well-established sequence (this exact structure is often called the "Bayesian workflow," most formally described by Gelman et al.). Follow it in this order, don't skip steps:

1. **Prior predictive check** — before fitting anything to real data, simulate data *from your priors alone* and check it produces plausible strain values (0–10 range, not absurd numbers). This catches badly specified priors before they contaminate a real fit.

2. **Fit the model on your real data** — run NUTS as specified in your model definition.

3. **Check convergence diagnostics** — R-hat ≈ 1.0 for every parameter, reasonable effective sample size, zero or near-zero divergences. **Do not proceed to interpret results if these fail** — this is the single most common mistake in student Bayesian projects: presenting posterior means from a model that didn't actually converge.

4. **Posterior predictive check** — simulate new data *from the fitted posterior* and compare it against your real held-out data. Does it look similar? This is your actual "does the model work" check, not just R-hat.

5. **Only then** compute your validation metrics (held-out MAE, calibration check, comparison against `composite_score`) and produce the results you show your professor.

If you skip straight to "fit and report the posterior mean," you have no way of knowing whether the numbers you're showing your professor are trustworthy or an artifact of a poorly converged sampler — this is the difference between doing this correctly and just producing output that looks right.

## 3. "Give context to AI and have it do this / switch between AIs to double-check" — is this sound?

Honest answer: **as a support tool, yes; as your actual verification method, no — and here's precisely why, not just a vague caution.**

- An LLM can write PyMC boilerplate for you correctly most of the time — the model specification we've built together is standard enough that any capable coding assistant can translate it into working code.

- **What an LLM cannot substitute for:** actually checking R-hat/divergences on *your* specific run, actually looking at *your* posterior predictive plots, actually verifying *your* data was joined/split correctly. These require you to run the code and inspect real diagnostic output — an LLM describing what good diagnostics "should" look like is not the same as you confirming your run actually has them.

- **Switching between different AI models to cross-check is a weak verification strategy specifically here**, because different LLMs are all working from similar training data about "how Bayesian workflows generally go" — they're not independently re-deriving correctness from your actual numbers, they're pattern-matching to similar-looking projects. Two AIs agreeing doesn't mean your model converged; it means two systems both produced plausible-sounding text.

- **The actual professional verification method:** run the diagnostics library functions yourself (ArviZ, which ships with PyMC, has `az.summary()` for R-hat/ESS and `az.plot_trace()`, `az.plot_ppc()` for visual checks) and *read the numbers/plots yourself*. This is the real check — not another LLM's opinion.

**Correct way to use AI here:** use one capable AI assistant to help you write and debug the PyMC code, then verify the results using the standard tools (ArviZ diagnostics) yourself, and understand what you're looking at well enough to explain it to your professor without relying on an AI's summary of your own results.

## 4. Which AI, and which tools (Colab / Jupyter / VS Code)?

**Coding environment — Jupyter-style notebooks are the correct choice for this specific task**, not a plain script in VS Code, and this isn't a stylistic preference — it's because Bayesian workflow is inherently iterative and visual: you fit, plot trace diagnostics, look at posterior predictive plots, adjust, refit — notebooks let you keep intermediate objects (the fitted model, the posterior samples) in memory between cells without rerunning the entire (potentially slow) NUTS sampling every time you want to check one more diagnostic plot. This matters a lot in practice — NUTS runs can take minutes; you don't want to rerun the whole thing to see a different plot.

Two good options:

- **Google Colab** — zero setup, free GPU/CPU compute, good for a class project where you don't want to fight environment/dependency issues. Install PyMC via `!pip install pymc` in the first cell. Downside: sessions can time out or disconnect during long NUTS runs, which is a real risk if your model takes a while to sample.

- **Local Jupyter (via Anaconda/Miniconda) or JupyterLab** — more reliable for longer runs, no timeout risk, but requires you to manage the PyMC install (PyMC has some non-trivial dependencies, particularly around compiled backends) — this can eat time troubleshooting environment issues that Colab avoids.

**VS Code** can run Jupyter notebooks too (via its Jupyter extension) if you prefer its editor — this isn't actually a separate choice from "notebooks," it's just a different interface to the same notebook format. If you're comfortable with VS Code already, using it with the Jupyter extension gets you the best of both (notebook-style iterative workflow + a full code editor for any supporting scripts).

**My concrete recommendation for your situation:** start in **Google Colab** for initial development and debugging (fast iteration, no setup friction), and if your Macro-level NUTS run turns out to take long enough to risk Colab disconnecting, move the final full training run to local Jupyter/VS Code with a stable, uninterrupted session.

**Which AI to use for code help:** any current-generation coding-capable assistant (Claude, ChatGPT, etc.) can write correct PyMC boilerplate for a model this well-specified — the actual differentiator won't be which AI you pick, it'll be whether you verify its output against real diagnostic checks yourself, per point 3 above. Don't spend time shopping between AI models for this; spend that time learning to read `az.summary()` output correctly.

## 5. How to make sure this is actually done right — a concrete checklist

Before showing your professor anything, confirm all of these, not just some:

- [ ] Data audit done: number of users, labeled epochs per user, reported explicitly (not assumed)

- [ ] Prior predictive check run and sane

- [ ] Model fit with ArviZ diagnostics checked: R-hat ≈ 1.0 for all parameters, zero/near-zero divergences, adequate effective sample size

- [ ] If diagnostics failed, you adjusted priors/reparameterized and refit — not just reported the failed run's numbers anyway

- [ ] Posterior predictive check plotted and visually reasonable

- [ ] Held-out validation done at session/user level, not row-level

- [ ] Results reported *with* uncertainty (credible intervals), not just point estimates

- [ ] Honest statement included about data volume limitations, given point 1 above

This is the actual, professional standard for "trained and validated a Bayesian hierarchical model" — not an AI-generated summary of results, but you having personally confirmed each of these against your real output.
